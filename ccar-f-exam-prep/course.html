Domain 1 · 27% of scored items

Agentic Architecture & Orchestration

This is the largest domain on the exam. It is about who decides what happens next: the model, or your code. It is also about what breaks when that line is drawn in the wrong place.

The scenario this domain runs on

You are building a multi-agent research system with the Claude Agent SDK. A coordinator agent takes a research topic, decides how to break it up, and delegates to four specialised subagents. The system's output is a comprehensive, cited report.

The coordinator delegates to:

web search document analysis synthesis report generation
3 of 6 creative-industry sectors the system covered in the exam guide's own failure case. Every subagent succeeded. The report read as finished, cited its sources, and silently omitted music, writing and film — and nothing in the output said so.

Each of the seven task statements below is a different place that system can go wrong. The loop never ends, or ends too early. The work is split badly. A subagent is sent off knowing nothing. A rule that had to hold every time was written as a sentence instead of as code.

Scenario switch Task Statements 1.4 and 1.5 move to a different scenario. The guide writes both of them in refund-and-verification vocabulary: identity checks before financial operations, and refunds above a threshold. So 1.4 and 1.5 run on the guide's Customer Support Resolution Agent instead. They are the only two sections in this domain that do, and each is flagged again when you get there.

Start hereThe words this domain is built on

agentic loop
The repeating cycle your code runs: send the conversation, read what came back, run any tools it asked for, send it again. The model does not loop. Your code does.
stop_reason
A field on every API response saying why the model stopped talking. It is the signal your loop reads to decide whether to send another request.
coordinator
The lead agent. It receives the query, decides how to split it, delegates, and combines what comes back. The guide also calls it the lead agent.
subagent
A separate Claude session with its own context window. It sees nothing of the parent conversation unless you write it into the prompt.
Task tool
The tool a coordinator calls to spawn a subagent. A coordinator cannot delegate at all unless "Task" is in its allowedTools.
hook
Your code, run by the SDK at a fixed point in the tool lifecycle. A hook runs every time. A prompt instruction runs most of the time.
fork_session
Branching one session into independent copies, so two approaches can be explored from the same analysis baseline without contaminating each other.
context cost
Tokens loaded before your first message. Everything a subagent is handed, and every tool result appended to history, costs tokens on every later turn.
Task Statement 1.1

Design and implement agentic loops for autonomous task execution

Every agent in the research system runs one of these loops. The coordinator runs one while it delegates. The web-search subagent runs its own while it searches. Whatever else the architecture gets right, each of those loops ends on one signal. It is not the model telling you it is finished.

Why it's tested

Items in this task statement offer you three plausible stopping conditions and one correct one. The plausible ones read the assistant's prose, count iterations, or check whether any text came back. All three fail in the same way: they infer a control decision from content. stop_reason is the field the API provides for that decision, and reaching for anything else is the most common wrong answer in Domain 1.

Start hereThree blocks this section keeps naming

tool_use block
A block inside the assistant's reply saying which tool to run and with what input. It carries an id, which you will need again.
tool_result block
The block you send back carrying what the tool returned. It goes in a message with "role": "user", not an assistant message.
tool_use_id
The field on a tool_result that names which tool_use it answers. One response can request several tools, so the pairing has to be explicit.

The mechanism, one turn at a time

  1. Your code sends messages[] — the entire conversation so far, not a summary of it.
  2. Claude replies. Your code reads one field on that reply: response.stop_reason.
  3. If it is "tool_use", the reply also carries one or more tool_use blocks. Your code runs every one of them.
  4. Your code appends two messages: the assistant's reply verbatim, then a "role": "user" message holding one tool_result per tool, each matched by tool_use_id.
  5. Back to step 1. The loop exits when stop_reason comes back "end_turn" — the model has nothing left to ask for and has written its answer.

KnowledgeWhat each stop_reason tells your loop to do

Four of the seven values decide whether another request goes out. Read them as instructions to your code, not as descriptions of the model's mood.

"tool_use"send again

The docs' wording: "Claude is calling a tool and expects you to run it." The reply also carries the tool_use blocks.

Your moveRun the tools, append the results, send.

"pause_turn"send again

The server-side sampling loop hit its own iteration limit mid-way through a server tool, such as web search.

Your moveSend the response back as-is. Run nothing.

"end_turn"loop ends

The docs call it "the most common stop reason" — Claude finished its response naturally.

Your moveReturn the answer. This is the exit.

"max_tokens"stop, but broken

Claude hit the max_tokens ceiling in your request. The reply is cut off mid-thought.

Your moveStop the loop, but never treat this as a finished answer.

More precise than the guide. The guide names two values, "tool_use" and "end_turn", and those two are the exam answer. The API documents seven. The three not shown above are "stop_sequence", "refusal" and "model_context_window_exceeded". The one that will actually bite you in production is "pause_turn": a loop written as while stop_reason == "tool_use" falls straight out of it and reports a half-finished search as the final answer.

KnowledgeWho picks the next step

This is the line between an agent and a workflow, and it is why the loop exists at all.

Pre-configured decision tree

A workflow

"Systems where LLMs and tools are orchestrated through predefined code paths."

Your code fixed the sequence of calls before the run began. Claude fills in each step, but never chooses the next one, so there is nothing for stop_reason to decide.

Model-driven decision-making

An agent

"Systems where LLMs dynamically direct their own processes and tool usage."

Claude reads the last tool result and decides which tool to call next. The loop is the machinery that carries that decision, one turn at a time.

The payload, both halves

Naming the blocks is not the same as seeing them. Here is one turn of the web-search subagent's loop, in full.

What comes back
// response
{
  "stop_reason": "tool_use",
  "content": [
    { "type": "text",
      "text": "Starting with recent coverage." },
    { "type": "tool_use",
      "id": "toolu_01A09q90qw90lq9",
      "name": "web_search",
      "input": { "query": "AI in film scoring" } }
  ]
}

Note the text block sitting beside the tool_use block. The model wrote a sentence and asked for a tool in the same turn. That is why "did any text come back?" answers nothing.

What you append
// two messages, in this order
{ "role": "assistant",
  "content": [ /* the array above, verbatim */ ] },

{ "role": "user",
  "content": [
    { "type": "tool_result",
      "tool_use_id": "toolu_01A09q90qw90lq9",
      "content": "[{\"title\":\"…\",\"url\":\"…\"}]",
      "is_error": false }
  ] }

The results travel in a user message. The tool_use_id has to match, because one response can request four searches at once and the model needs to know which answer is which.

Casing changes with the layer. On the Claude API a tool_result block carries is_error, snake_case. On the MCP side, a tool result carries isError, camelCase. Same idea, two spellings, and Domain 2 is where the MCP one lives.

SkillWriting the control flow

  • Drive the loop off stop_reason and nothing else.
  • Handle every tool_use block in a response, not just the first. A coordinator that delegates in parallel emits several at once.
  • Append the assistant's turn before the tool results. Dropping it breaks the pairing the tool_use_id depends on.
  • Send the whole history every time. Trimming it here is a Domain 5 decision, made deliberately, not a default.
  • Keep an iteration ceiling and a human checkpoint. Both are guardrails around the signal, not replacements for it.
Before

The loop ends when the prose looks final

Two stopping conditions, neither of them the signal.

for i in range(10):
    r = client.messages.create(**kw)
    if "done" in text_of(r).lower():
        break
    run_tools_and_append(r, kw)

On a long topic the subagent is cut off at ten turns with three sources gathered. On a short one it stops the first time Claude writes "that's done" while still holding a pending tool_use block. The search never runs, and its result is never appended.

After

The loop ends when the API says the turn ended

One stopping condition, read from the response object.

r = client.messages.create(**kw)
while r.stop_reason == "tool_use":
    kw["messages"] += [
        assistant_turn(r),
        tool_results_turn(r),   # all blocks
    ]
    r = client.messages.create(**kw)

What changed: the condition moved from the reply's content to the reply's metadata. The cap does not disappear. It moves out to a wrapper, where a run that exceeds it is logged as a fault instead of passing for a finished answer.

Anti‑patternThree ways this breaks in production

  • Parsing the assistant's text for a completion phrase. Text is content, not a control signal, and the model was never asked to emit one.
  • Letting the iteration cap be what actually ends most runs. The agent is being cut off mid-task, and the truncated report looks identical to a finished one.
  • Treating "the response contains text" as "the turn is complete." The payload above shows a text block and a tool_use block in the same reply.
The decision test Is the thing that ends your loop a field on the response object? Yes → it is stop_reason, and the loop ends exactly when the turn does. No → you are reading prose or counting turns, and the loop will end at the wrong time in both directions: too early on short tasks, too late on long ones.
Takeaway
  • Check stop_reason, not the text of the reply.
  • Only "end_turn" ends the loop. "tool_use" and "pause_turn" both mean send another request.
  • Tool results go back in a "role": "user" message, one tool_result per tool_use_id.

Task Statement 1.2

Orchestrate multi‑agent systems with coordinator‑subagent patterns

The research system's coordinator decides how to cut up a topic before any subagent runs. Everything downstream inherits that cut, and no subagent can see enough to notice it was wrong.

Why it's tested

These items describe a system where every component reports success and the output is still wrong. Three of the four answers blame a downstream agent. The skill being measured is reading the coordinator's log instead: a report with clean gaps rather than sloppy errors is a decomposition fault, and the agents that executed it were working correctly within the scope they were handed.

Start hereThree words for the shape of this system

hub-and-spoke
One coordinator at the centre, subagents on the spokes. Every message travels along a spoke. No spoke connects to another spoke.
decomposition
The coordinator's act of cutting one query into subtasks. It happens once, before delegation, and nothing downstream can revise it.
iterative refinement
Running synthesis, checking the result for gaps, re-delegating targeted follow-ups, and synthesising again — instead of a single pass.

The mechanism, in order

  1. The coordinator reads the query and judges how complex it is.
  2. It decomposes the query into subtasks, and decides how many subagents that warrants.
  3. It spawns them, handing each a distinct slice — its own subtopic, or its own source type.
  4. Each subagent works alone. It cannot see what the others were asked or what they found.
  5. Results return to the coordinator, which aggregates them and reads the combined output for gaps.
  6. If there are gaps, it re-delegates targeted follow-ups and synthesises again.
Interactive · how many subagents does this query warrant?
Choose a query type — the fan-out and the tool-call budget move with it.
Scaling figures: Anthropic Engineering, "How we built our multi‑agent research system" — one agent with 3–10 tool calls for simple fact-finding, 2–4 subagents with 10–15 calls each for direct comparisons, more than 10 for complex research.

KnowledgeWhat the coordinator owns

  • It routes everything. Results, errors and follow-up requests all travel back through the coordinator, which is what makes the system observable and its error handling consistent.
  • It decides the fan-out. Matching the number of subagents to real query complexity is a coordinator decision, not a fixed pipeline.
  • It aggregates. Only a subagent's final message reaches it. Intermediate tool calls and reasoning stay inside that subagent's own context window.
  • It owns the decomposition. An overly narrow decomposition leaves parts of a broad topic unassigned, and nothing downstream can correct it.

Vague briefs produce duplicated work. Anthropic's own early runs asked subagents to "research the semiconductor shortage" and got one subagent on the 2021 automotive chip crisis while two others both investigated 2025 supply chains. The fix was to give each subtask four things: an objective, an output format, guidance on which tools and sources to use, and clear task boundaries.

SkillCutting the query

  • Partition by subtopic or by source type, so two subagents cannot land on the same ground.
  • Give every subtask the four-part brief above. A subagent cannot notice overlap, because it cannot see the others.
  • Run synthesis, read the output for gaps, re-delegate targeted follow-ups, run synthesis again. One pass has no mechanism for catching a bad cut.
  • Scale the fan-out to the query, not to the pipeline you happen to have built.
Before

The cut that loses half the topic

Query: "impact of AI on creative industries."

// coordinator log
subtasks = [
  "AI in digital art creation",
  "AI in graphic design",
  "AI in photography",
]

All three subagents succeed. The synthesis agent produces coherent, cited output. Music, writing and film were never assigned to anyone, so nothing in the system is in a position to report them missing. The three named sectors are all it was ever asked about.

After

The cut that spans the topic, then checks itself

Same query, sectors enumerated before they are assigned.

// coordinator log
sectors  = ["visual art","music","writing",
            "film","games","design"]
subtasks = [one per sector, each with
            objective, output format,
            sources, boundaries]
then: synthesise → read for gaps →
      re-delegate → synthesise

What changed: the coordinator enumerates the space before it cuts, and the second pass gives the system a place to notice a gap. The subagents did not get better. The plan did.

Anti‑patternWhere these systems quietly fail

  • Blaming the subagent whose output looks thin. It answered the question it was given.
  • Running every query through the full pipeline. A simple fact-finding query does not warrant ten subagents.
  • Treating synthesis as the last step. With no gap check after it, a bad cut ships as a finished report.
  • Assuming subagents will notice they overlap. They cannot see each other's assignments or findings.
The decision test Did a component fail, or did every component succeed? Something failed → debug that component. Everything succeeded and the output is still wrong → the fault is in the decomposition, and the coordinator's log is where you will see it.
Takeaway
  • Clean gaps rather than sloppy errors point at the coordinator's cut, not the subagents.
  • Fan-out scales with query complexity: 1 agent, 2–4 subagents, or more than 10.
  • A single synthesis pass has nowhere to catch a bad decomposition, so add the gap check.

Task Statement 1.3

Configure subagent invocation, context passing, and spawning

1.2 said each subagent has its own context window. This is the section that says exactly what crosses that boundary and what does not. The synthesis subagent cannot synthesise findings it was never handed.

Why it's tested

The failure these items describe is a synthesis subagent producing a thin or unsourced report while the search subagents plainly found good material. The cause is that the findings were never written into the synthesis subagent's prompt. Nothing in the system errors, because from the subagent's side nothing was wrong. It summarised everything it had.

Start hereHow a subagent is defined and launched

AgentDefinition
The configuration object for one subagent type. Two fields are required: description, which tells Claude when to use it, and prompt, its system prompt.
Agent tool
What Claude calls to spawn a subagent. The docs note it "appears as "Agent" in tool_use blocks but as "Task" in the system:init tools list."
prompt string
The text passed in the Agent tool call. The docs call it "the only content you pass from parent to subagent."
fork
The one kind of subagent that does inherit the parent conversation. Everything else in this section describes a non-fork subagent.

The mechanism, in order

  1. You declare each subagent type as an AgentDefinition in the agents option.
  2. "Task" must be in the coordinator's allowedTools, or it cannot delegate at all.
  3. Claude calls the Agent tool, picking a subagent type by its description.
  4. A fresh context window opens. It contains the subagent's own system prompt, the prompt string, tool definitions and project CLAUDE.md — and nothing of the parent's conversation.
  5. The subagent works. Its intermediate tool calls and reasoning never leave that window.
  6. Its final message comes back as the Agent tool's result. That one message is all the coordinator sees.
Interactive · what crosses the context boundary
Choose how the subagent starts — the boundary lets different things through.
Two windows, drawn apart because they are apart. Source: Claude Docs, "Subagents in the SDK" — the what-subagents-inherit table.

More precise than the guide. The guide says subagent context "must be explicitly provided in the prompt," which is the exam answer. The docs are sharper about what that leaves: a non-fork subagent's context window "starts fresh, with no parent conversation, but isn't empty." It still receives project CLAUDE.md, its own system prompt and tool definitions. "Starts empty" is the wrong mental model. What it starts without is the parent's history, the parent's system prompt and preloaded skill content.

The payload, both halves

Defining the subagent
# only description and prompt are required
agents={
  "synthesis": AgentDefinition(
    description="Combines findings into a
      cited report. Use after research.",
    prompt="You synthesise research findings.
      Preserve every claim's source.",
    tools=["Read"],       # omit → inherits all
    model="sonnet",
  ),
}
allowed_tools=["Agent", "Read", "Grep"]

Leave tools out and the subagent inherits every tool available to subagents. Setting it is the tool restriction the guide names. It is how you keep a synthesis agent from running web searches, which is the Domain 2.3 principle enforced in configuration.

Spawning three in parallel
// one assistant turn, three Agent calls
"content": [
  { "type": "tool_use", "name": "Agent",
    "input": { "subagent_type": "search",
      "prompt": "Sector: music. Findings so
        far: …[pasted in full]…" } },
  { "type": "tool_use", "name": "Agent",
    "input": { "subagent_type": "search",
      "prompt": "Sector: film. …" } },
  { "type": "tool_use", "name": "Agent",
    "input": { "subagent_type": "search",
      "prompt": "Sector: writing. …" } }
]

Three calls in one response run concurrently, so they finish in the time of the slowest. The same three issued across three turns run end to end.

SkillPassing context deliberately

  • Paste prior findings into the subagent's prompt in full. Nothing else carries them.
  • Use a structured data format that keeps content separate from metadata, so attribution survives the next hop. The claim, the source URL, the document name and the page number each get their own field.
  • Emit multiple Agent tool calls in a single coordinator response to get real parallelism.
  • Write the prompt as research goals and quality criteria, not step-by-step procedure, so the subagent can adapt when what it finds differs from what you expected.
Before

A prompt that assumes inheritance

"prompt": "Synthesise the research
  findings into a cited report."

The subagent has no findings. It writes a plausible, well-structured report from its own general knowledge, cites nothing specific, and returns successfully. The coordinator has no signal that anything went wrong.

After

A prompt that carries the findings

"prompt": "Synthesise these findings.
  [{claim, evidence, source_url,
    doc_name, page, published}, …]
  Quality bar: every claim keeps its
  source. Flag any sector with no
  supporting finding."

What changed: the findings moved into the prompt string, and the structure keeps each claim attached to its source. The last line gives the subagent a way to report a gap rather than paper over it.

Anti‑patternThree assumptions that produce silent bugs

  • Assuming a subagent can see what a sibling found. Siblings share nothing at all.
  • Assuming a second invocation remembers the first. Memory is not shared between invocations.
  • Blending claims and sources into prose before passing them on. Attribution is what gets lost, and it is unrecoverable downstream.
The decision test Is the fact written into the Agent tool's prompt string? Yes → the subagent has it. No → it does not, whatever else is true of the session, and it will answer anyway rather than tell you it is missing something.
Takeaway
  • The prompt string is the only content that crosses from parent to subagent.
  • Omitting tools from an AgentDefinition gives the subagent every tool, not none.
  • Parallelism comes from multiple Agent calls in one response, not from several turns.

Task Statement 1.4

Implement multi‑step workflows with enforcement and handoff patterns

Scenario switch This section runs on the Customer Support Resolution Agent. The guide writes 1.4 in refund-and-verification vocabulary, and the ordering constraint it tests, identity before money, has no equivalent in the research system. The tools are get_customer, lookup_order, process_refund and escalate_to_human.

Some orderings can be requested. Others have to be made impossible to violate. This section is about telling the two apart, and about what a human needs when the agent gives up.

Why it's tested

The guide's own sample question puts four options in front of you: a programmatic prerequisite, a stronger system prompt, few-shot examples, and a routing classifier. Three of them are ways of making the model more likely to comply. The item is checking whether you know that "more likely" is the wrong category of answer when the failure has a dollar amount attached.

Start hereTwo words for the same constraint

programmatic enforcement
Code that makes a step impossible until its prerequisite has run. The model's cooperation is not part of the mechanism.
prompt-based guidance
An instruction in the system prompt. It raises compliance and leaves a non-zero failure rate, because the model can still reason past it.
structured handoff
A fixed set of fields compiled when escalating to a human, because that human cannot see the conversation transcript.

The mechanism, in order

  1. The customer asks for a refund, giving an order number but no account detail.
  2. The agent decides which tool to call. Nothing yet stops it choosing process_refund.
  3. A prerequisite check runs before the call executes, asking whether get_customer has already returned a verified customer ID.
  4. If it has, the call proceeds. If it has not, the call is refused and never reaches the tool.
  5. The refusal redirects the agent — to run verification first, or to escalate.
Interactive · the same request under two enforcement models
Choose how "verify first" is enforced — the outcomes below change with it.
Prompt-based guidance: the instruction is followed most of the time. The 12% figure is the exam guide's own production number for this scenario, and those runs refund a misidentified account.

KnowledgeWhich constraint needs which mechanism

  • A prerequisite gate makes the downstream call impossible. A prompt instruction makes it unlikely.
  • Deterministic compliance is required where a miss has a financial or irreversible consequence. Identity verification before a financial operation is the guide's own example.
  • Below that bar, a prompt instruction is the cheaper and perfectly reasonable first move.
  • A human taking an escalation cannot see the conversation transcript, so anything they need has to be compiled into the handoff itself.

SkillThe two things this section asks you to build

  • Block process_refund and lookup_order until get_customer has returned a verified customer ID.
  • Decompose a multi-concern message into distinct items, investigate each in parallel against shared context, then synthesise one unified resolution rather than answering the first issue and dropping the rest.
  • Compile the handoff with the customer ID, the root cause, the amount in question and a recommended action.
Before

The handoff a human cannot act on

escalate_to_human({
  "reason": "Customer is unhappy about
    a refund. Please assist."
})

The human opens this with no transcript. They restart the investigation from who the customer is, and the customer repeats everything. The escalation cost more than no agent at all.

After

The handoff that carries the case

escalate_to_human({
  "customer_id": "C-88431",
  "root_cause": "Item shipped damaged;
    photo evidence on file.",
  "amount": 640.00,
  "recommended_action": "Full refund.
    Exceeds the $500 agent ceiling.",
  "attempted": ["get_customer",
    "lookup_order", "process_refund"]
})

What changed: four named fields replaced one sentence. The human now opens a case they can decide on immediately, and the attempted list stops them repeating work the agent already did.

Anti‑patternAnswers that address the wrong layer

  • Rewriting the system prompt to say verification is mandatory. It already said that. The failure rate is the point.
  • Adding few-shot examples of the correct order. Same category of fix, same non-zero failure rate.
  • Building a routing classifier that enables a subset of tools. That changes which tools exist, not the order they run in. Ordering is the actual problem.
The decision test Can this step be skipped occasionally without anyone being harmed? Yes → a prompt instruction is proportionate and cheap. No → nothing that depends on the model complying is an answer. Block the call in code until the prerequisite has actually returned.
Takeaway
  • If the failure has a dollar amount attached, a better prompt is the wrong category of fix.
  • A prerequisite gate blocks the call. Prompt-based guidance only makes compliance likely.
  • An escalating human has no transcript, so send customer ID, root cause, amount and recommended action.

Task Statement 1.5

Apply Agent SDK hooks for tool call interception and data normalization

Scenario switch This section stays on the Customer Support Resolution Agent. The guide writes 1.5 in the same vocabulary as 1.4 — a refund ceiling, heterogeneous formats coming back from different backend tools. It is the second and last section in this domain that leaves the research system.

1.4 said some rules have to be impossible to break. Hooks are the mechanism that makes them impossible. They are your code, run by the SDK at a fixed point, and they do not negotiate.

Why it's tested

Items here describe a rule, such as a refund ceiling or a required date format, and ask which mechanism enforces it. The discriminator is not whether you know hooks exist. It is whether you pick the right one: a rule that must hold before an action happens needs a hook that runs before the action, and there is only one of those.

Start hereThe two events and the field that blocks

PreToolUse
The docs define it in five words: "Before a tool call executes. Can block it."
PostToolUse
The docs define it in four: "After a tool call succeeds." The call already happened, so this event cannot prevent anything.
permissionDecision
The field a PreToolUse hook sets to "deny" to refuse a call. Exit code 2 does the same thing from a shell hook.

The mechanism, in order

  1. Claude decides to call process_refund with an amount.
  2. Before the call executes, the SDK runs your PreToolUse hook and hands it the tool name and its input.
  3. Your hook reads the amount and decides. This is ordinary code — no model is involved.
  4. Returning permissionDecision: "deny" refuses the call. It never reaches the tool.
  5. The reason you supply goes back to Claude, which can then take the alternative path — here, escalate_to_human.

Choose an amount — the hook's decision, not the model's, picks the path.
$180 is under the ceiling, so the hook allows the call and the refund tool runs. Event definitions: Claude Docs, "Hooks reference."

The payload that does the blocking

The guide calls this "tool call interception." What it is, concretely, is a JSON object your hook returns.

// returned by a PreToolUse hook
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Refund of $800 exceeds the $500 agent ceiling. Escalate instead."
  }
}

Two ways to say deny. A hook can return the JSON above, or exit with code 2, which the docs define as a blocking error. Either refuses the call. A command, http or mcp_tool hook that times out on PreToolUse does not block the call. A gate that has to hold therefore cannot depend on a slow external service answering in time.

KnowledgeWhich event, and what it can do

Runs before

PreToolUse

"Before a tool call executes. Can block it."

Use it when the damage is preventable: a refund over the ceiling, a write to a path that should be read-only, an operation whose prerequisite has not run. This is the only event that can stop something happening.

Runs after

PostToolUse

"After a tool call succeeds."

Use it when the damage is already done and only needs tidying: reshaping a result, logging it, flagging it. Choosing this event for a rule that had to hold is the classic wrong answer, because by the time it runs the refund has been issued.

SkillNormalising with PostToolUse

Three backend tools, three ways of saying the same two things. Without a normalising hook the agent has to work out each tool's conventions before it can reason about the case. It gets that wrong when a numeric status code looks like an amount.

Before the hook

What the three tools return

get_customer  → "since": 1697040000
lookup_order  → "placed": "2024-03-11T09:00Z"
process_refund→ "status": 2

A Unix timestamp, an ISO 8601 string and a numeric status code. The agent has to infer each convention from context, every turn, for every tool.

After the hook

What the agent actually sees

get_customer  → "since": "2023-10-11"
lookup_order  → "placed": "2024-03-11"
process_refund→ "status": "pending"

What changed: one PostToolUse hook converts all three before the model reads them. The reasoning the agent saves goes to the case instead of the formats.

Anti‑patternTwo ways to pick the wrong tool

  • Enforcing a ceiling in PostToolUse. The refund has already been issued by the time it runs. It can log the breach, not prevent it.
  • Using a hook for guidance that is fine to get wrong occasionally. Hooks are code you now maintain. A prompt instruction is cheaper and sufficient below the deterministic bar.
The decision test Must this rule hold every single time? Yes → the business rule requires guaranteed compliance, so use a PreToolUse hook, because it runs before the action and can refuse it. No → a prompt instruction, which is cheaper and carries a failure rate you have decided you can live with.
Takeaway
  • PreToolUse runs before the call and can block it. PostToolUse runs after it succeeds and cannot.
  • A hook denies by returning permissionDecision: "deny", or by exiting with code 2.
  • Normalise Unix timestamps, ISO 8601 dates and numeric status codes in PostToolUse, before the model reads them.

Task Statement 1.6

Design task decomposition strategies for complex workflows

1.2 was about cutting a research topic across subagents. This is the same question one level down: given one large job, do you write the steps in advance, or let each step decide the next?

Why it's tested

The symptom these items describe is always the same: one pass over a large input comes back uneven. Detailed feedback on some files, superficial on others, obvious bugs missed, and the same pattern flagged in one file and approved in another. The trap answer is a bigger context window. The concept being tested is that this is attention dilution, and a larger window does not fix it.

Start hereThe two shapes and the failure they fix

prompt chaining
Breaking a task into a fixed sequence of focused passes, decided before you start. Each pass sees less, so each pass sees it properly.
dynamic decomposition
Generating the next subtask from intermediate findings. The guide calls it dynamic adaptive decomposition, and Anthropic calls it orchestrator-workers. The plan does not exist until the work produces it.
attention dilution
What goes wrong when one pass carries too much: depth becomes uneven and judgements become inconsistent across the same input.

The mechanism, in order

  1. Ask whether you can name the steps before seeing the input.
  2. If you can, write them as a fixed chain, each pass scoped to one concern.
  3. Between passes you may add a programmatic check, confirming the previous pass stayed in scope.
  4. If you cannot name the steps, start with a pass that maps the territory instead.
  5. Generate the next subtasks from what that pass actually found, and repeat as dependencies surface.

KnowledgeWhat decides between them

  • Prompt chaining fits predictable multi-aspect reviews, where the aspects are known before the input is seen.
  • Dynamic decomposition fits open-ended investigation, where the useful subtasks depend on what the first pass turns up.
  • A chain can carry a programmatic check between steps, confirming the previous pass stayed in scope before the next one runs.
  • The same scaling instinct from 1.2 applies here: the number of passes should track the real size of the job, not a habit.

SkillSplitting a review that came back uneven

Before

One pass over 14 files

Every file, every concern, one prompt.

The output is detailed on some files and superficial on others, misses obvious bugs, and flags a pattern as a problem in one file while approving identical code elsewhere in the same PR. Nothing is broken. There was simply more input than one pass could attend to evenly.

After

Fourteen local passes, then one integration pass

Per-file passes for local issues, a separate pass for cross-file data flow.

What changed: each pass now carries one file. Depth is even because every pass has the same amount to attend to, and the contradiction disappears because one judgement is no longer competing with thirteen others. The integration pass is what still catches issues that only exist between files.

Anti‑patternFixes that do not address attention

  • Moving to a model with a larger context window. The files already fit. Fitting was never the problem.
  • Requiring developers to submit smaller pull requests. That moves the work to people instead of fixing the system.
  • Running three passes and reporting only findings that appear in two. Real bugs are often caught intermittently, so consensus filtering suppresses them.
  • Writing the full subtask list up front for an open-ended job. You are guessing at dependencies you have not discovered yet.
The decision test Can you name the steps before you look at the input? Yes → prompt chaining: fix the sequence, scope each pass to one concern. No → dynamic decomposition: map first, then let each finding generate the next subtask.
Takeaway
  • Uneven depth and contradictory findings from one pass are attention dilution, not model quality.
  • The fix is per-file local passes plus a separate cross-file integration pass.
  • Open-ended jobs like "add comprehensive tests to a legacy codebase" get mapped first and planned second.

Task Statement 1.7

Manage session state, resumption, and forking

The research system's codebase investigation ran for a day and a half. Coming back to it is three different decisions, and the exam is interested in the one people get wrong: resuming a session whose stored tool results have quietly stopped being true.

Why it's tested

Resuming feels like the safe default, and it usually is. The item that catches people describes a session resumed after the code changed. Everything the session learned comes back intact, including the parts that are now false, and the agent reasons from them confidently because nothing marks them as stale.

Start hereThree ways back into a conversation

resume
claude --resume <name>. Restores the full history, "including tool calls and results," in the docs' words.
branch
/branch, or --fork-session from the CLI. Copies the conversation so far into a new session and switches you into it. The original is untouched.
fork_session
The guide's name for the same mechanism. It is what you use to explore two divergent approaches from one shared analysis baseline.
stale tool result
A restored result that was true when it was recorded and is not any more. Nothing in a resumed session marks it.

The mechanism, in order

  1. Name the session as you work, so it is resumable by name rather than buried in a picker. Use claude -n refund-trace at startup, or /rename refund-trace later.
  2. Later, decide what you actually need back: everything, a copy to diverge from, or only the conclusions.
  3. --resume <name> restores the whole conversation, tool results included, exactly as recorded.
  4. /branch copies it and switches you into the copy, leaving the original in the picker to return to.
  5. A fresh session with a written summary carries the conclusions and drops the detail — which is the right trade when the detail has gone stale.
Interactive · the same session, three ways to continue it
Choose what you need back — each option trades detail against staleness.
Three continuations of one session. Mechanism: Claude Docs, "Manage sessions" — what a resumed session restores, and what /branch copies.

The commands

# name it, so it is resumable by name later
claude -n refund-trace            # at startup
/rename refund-trace              # mid-session

# come back to it
claude --resume refund-trace       # named session, directly
claude --resume                   # the picker
claude --continue                 # most recent in this directory

# split it
/branch try-streaming-approach    # from inside the session
claude --continue --fork-session    # from the CLI

More precise than the guide. The guide says starting a new session with a structured summary is more reliable than resuming with stale tool results. The docs show Claude Code offering exactly that choice for you: resuming a session over 100,000 tokens after about an hour idle opens a dialog with Resume from summary, which runs /compact immediately, and Resume full session as-is. The guide's judgement call is a built-in prompt, but only above that size and idle threshold. Below it, the decision is still yours.

A fork in a new process starts without your permission grants. /branch keeps running in the same process, so "Allow for this session" approvals carry over. --fork-session starts a separate process, which begins with none of them and re-prompts. Same conversation, different permission state.

KnowledgeWhat a resumed session restores

  • The full conversation, including tool calls and their results, exactly as recorded.
  • The model the session was using, and the permission mode it was in, with documented exceptions.
  • A tool still running when the previous process ended does not finish or re-run. Claude continues without its output.
  • Not every launch flag. --mcp-config, --settings, --plugin-dir and --add-dir all have to be passed again.

SkillChoosing the continuation

  • Resume by name when the session's findings are still accurate.
  • Branch when you want two approaches from one shared analysis baseline, such as two testing strategies or two refactors.
  • Start fresh with an injected summary when the prior tool results have gone stale.
  • When you do resume after changes, name the changed files explicitly so the agent re-checks only those, instead of trusting stale results or re-exploring everything.

Anti‑patternTwo habits worth breaking

  • Resuming by reflex after the codebase moved. The stale results come back looking exactly as authoritative as the accurate ones.
  • Re-running the whole exploration because something changed. Naming the changed files gets you a targeted re-analysis instead.
The decision test Are the session's stored tool results still true? Yes → resume by name; you get the detail back for free. No → start fresh with a written summary, or resume and name exactly which files changed. Never resume and say nothing.
Takeaway
  • Resume restores everything, including results that have since become false.
  • /branch and --fork-session copy the conversation and leave the original intact.
  • When the old tool results are stale, start fresh with a summary, or resume and name the changed files.

Task Statement 2.1

Design effective tool interfaces with clear descriptions and boundaries

Your support agent keeps calling get_customer when someone asks about an order. Nothing is broken. The two tools simply look identical to the model, because the only thing it reads when choosing is the description.

Why it's tested

The exam puts four plausible fixes for this bug side by side. Three are heavier machinery: few-shot examples, a keyword routing layer, merging the two tools into one. The right answer is the cheapest — expand the descriptions. What's being tested is whether you reach for the root cause before you reach for infrastructure.

Start hereThree terms this section depends on

Tool description
The natural-language text attached to a tool definition. Claude reads it to decide whether this is the tool for the current turn. It is prose, not documentation for humans.
inputSchema
The JSON Schema for a tool's arguments — which fields exist, their types, which are required. It constrains the shape of a call, but it does not explain when to make one.
Tool selection
The model's choice of which tool to call, out of everything it has been given. Selection happens before any argument is filled in, and descriptions are the main input to it.

MechanismWhat actually happens at selection time

One message from the customer — "check my order #12345" — and two candidate tools. Flip between the two description qualities and watch where the call lands.

Interactive · same query, two description qualities
Minimal: both descriptions are one interchangeable line, so the order query lands on get_customer a large share of the time. Selection is close to a coin flip.

KnowledgeThe description is the routing table

  • Tool descriptions are the primary mechanism an LLM uses to select a tool. Anthropic's tool-use documentation calls the description "by far the most important factor in tool performance."
  • The guidance is at least three to four sentences per tool, and more when the tool is complex. One line is not a description.
  • An inputSchema does not rescue a thin description. The schema says what a valid call looks like; it never says when to make one.
  • The system prompt can override a good description. A keyword-sensitive instruction like "for anything about orders, use the order tool" fires on the word, not the intent.
  • Naming carries weight too. Anthropic's engineering guidance recommends a common prefix for related tools, because "tool overlap and vague purposes can confuse agents about which ones to use."

SkillWhat a rewritten description actually looks like

This is the whole fix for the misrouting bug above. Not a new tool, not a router — the same two tools, described properly.

SkillSplitting a tool that does too much

Sometimes the description can't be fixed, because the tool genuinely does several unrelated things. Your agent has one: get_account_info returns a profile, a billing history, or a list of open tickets — depending on how it was asked. No description can make that predictable.

One vague contract
get_account_info(customer_id,
                 include?)

→ sometimes a profile
→ sometimes billing rows
→ sometimes open tickets
→ caller can't predict which

The return shape changes with the request. Downstream turns have to branch on what came back.

Three defined contracts
get_customer(customer_id)
→ profile + account status

                    months)
→ dated charge rows

→ ticket ids + statuses

Each tool has one job, one input contract, one output shape. Selection gets easier and so does everything downstream.

As the exam words it

The guide teaches this same move on a research tool rather than a support one. It splits a generic analyze_document into extract_data_points, summarize_content, and verify_claim_against_source — three purpose-specific tools with defined input/output contracts, replacing one that did all three.

SkillThe rest of the fix

  • Include one or two example queries in the description. They cost little and resolve the ambiguous phrasings you didn't anticipate.
  • State the boundary explicitly: name the competing tool and say when to prefer it.
  • Audit the system prompt for keyword-sensitive instructions before rewriting any description. One sentence there can be what's actually driving the misrouting.
  • Give related tools a shared prefix so their grouping is visible at a glance.
The decision test Can a stranger read the two descriptions and always pick the right tool? If yes, the descriptions are done. If no, the model can't either — and no amount of few-shot examples will change that.

Anti‑patternFixes that skip the root cause

  • Adding five to eight few-shot examples to correct the routing. They cost tokens on every request and leave the thin description in place, so novel phrasings still misroute.
  • Parsing the customer's message for keywords and pre-selecting the tool. It bypasses the language understanding you're paying for, and it breaks on the phrasings you didn't anticipate.
  • Merging get_customer and lookup_order into one lookup_entity that guesses the backend. Occasionally a defensible architecture — but a far larger change than a description rewrite when the descriptions were simply thin.
Takeaway
  • The description is the routing table. A thin description is a routing bug.
  • Fix misrouting at the description first; few-shot examples and routing layers are heavier and come later.
  • Check the system prompt too — one keyword-sensitive sentence can override every description you wrote.

Task Statement 2.2

Implement structured error responses for MCP tools

When a tool call fails, the agent never sees your stack trace or your logs. It sees one short block of text that you chose to send back. What you put in that block decides whether the agent recovers or gives up.

Why it's tested

Every wrong answer in this area looks like responsible engineering. Retry with exponential backoff. Catch the timeout and return an empty list. Let the exception bubble up and stop the run. Each one is a normal instinct. Each one also deletes the information the agent needed in order to recover. The exam is checking whether you can tell tidy error handling apart from useful error handling.

Start hereThree more words this section depends on

MCP, MCP server and tool are defined at the top of this domain. These three are new here.

MCP client
The piece inside the host application that opens a connection to one MCP server and speaks the protocol to it. It relays calls and results; it does not decide anything.
Tool
One named action a server offers — lookup_order, process_refund. Claude decides to call it; the client performs the call.
JSON-RPC
The message format MCP speaks over the wire. Every request comes back as exactly one of two things: a result, or an error. That either/or is the whole basis of this task statement.
Tool result
What a tools/call returns. It holds a content array of text blocks, plus an optional isError flag. This is the block you are designing.

KnowledgeWhere the failure actually happens

  1. The user asks a question. Your app fetches the server's tool list and hands it to Claude with the question.
  2. Claude replies with a tool_use block naming lookup_order.
  3. Your app relays it to the MCP server as tools/call. The client carries it; it decides nothing.
  4. The server runs the real query, and the order database never answers.
  5. The server returns a result with isError: true and whatever text you wrote. This is the only step you control.
  6. Your app appends it as a tool_result with is_error: true. That text is everything Claude learns about the failure.

KnowledgeTwo channels: which failures reach the model

MCP can report a failure in two different ways, and only one of them puts text in front of Claude. Picking the wrong one is how a failure becomes invisible.

Channel 1

Protocol error

The call never reached a tool.

{
  "jsonrpc": "2.0", "id": 3,
  "error": {
    "code": -32602,
    "message": "Unknown tool: lookup_ordr"
  }
}

When: the tool name doesn't exist, the arguments don't match the schema, or the server itself fell over. There was nothing to run.

Who reads it: the MCP client. Claude is never shown this text.

Channel 2

Tool execution error

The tool ran. The work failed.

{
  "jsonrpc": "2.0", "id": 4,
  "result": {
    "content": [{ "type": "text",
      "text": "Order service timed out after 5s." }],
    "isError": true
  }
}

When: an upstream API was down, the input was valid but wrong, or a business policy refused the request.

Who reads it: Claude. This text lands in its context and it reasons over it.

Ask one question: did a tool actually run? Yes → it belongs in isError, where the model can read it and adapt. No → it is a protocol error, and the model is never told.

Two spellings, same idea. On the MCP side the flag on a tool result is isError. On the Claude API side, the matching flag on a tool_result content block is is_error. Different casing, different layer, one concept. Expect the exam to use either.

KnowledgeFour categories the exam names

The flag tells the agent that something failed. Only the category tells it what to do next — and the four correct next moves are all different.

transientretryable

The service is temporarily unwell. A timeout, a rate limit, a 503.

"Rate limit exceeded.
 Retry after 60 seconds."

Agent's move Wait, then call the same tool again with the same arguments.

validationretryable

The agent's arguments were wrong. The tool is fine.

"order_id must be 8 digits.
 Received 'ABC123'."

Agent's move Fix the argument, then call again. Retrying unchanged would fail identically.

businessnot retryable

The request is well-formed and permitted. Policy says no.

"Refunds are not available
 more than 90 days after
 delivery."

Agent's move Stop, and relay this explanation to the customer in its own words.

permissionnot retryable

The caller isn't allowed to do this at all.

"This agent role lacks the
 refund:write scope."

Agent's move Escalate to a human. No wording of the request will change the answer.

A fifth case that is not an error at all. "The search API timed out" and "the search ran and matched nothing" both arrive as no data. The first needs a retry decision. The second is a finished, correct answer. Return the empty one as a normal success with zero results, explicitly — or the coordinator will keep retrying a perfectly healthy service.

  3. Either retries forever, or abandons a call that would have worked on the second attempt.
  1. Reads transient and isRetryable: true — this is worth another attempt.
  2. Waits 60 seconds, then re-issues the same call.
  3. If it still fails, escalates with the attempted query attached, so the human starts informed.
Same outage, same isError: true. The only difference is four extra fields — and they are the difference between a recovery and a dead end.

SkillWhat to put in the payload

  • Name the category. The exam's own field is errorCategory, valued transient, validation, or permission.
  • State retryability as a boolean, not an implication. isRetryable: true removes the guesswork.
  • For a business rule violation, set retriable: false and write the message so the agent can relay it to a customer as-is. An internal policy code forces the agent to invent an explanation.
  • Write the message instructively. "Rate limit exceeded. Retry after 60 seconds." says what to do. "failed" says nothing.
  • Implement local error recovery within the subagent for transient failures. Propagate to the coordinator only what could not be resolved locally — with the partial results and what was attempted.
  • Mark a genuine zero-match result as a success, not as an absence.

Anti‑patternThree ways to destroy recoverable context

  • Retry internally with backoff, then return "search unavailable." The coordinator never learns the attempted query, the partial results, or the alternatives it could have tried.
  • Catch the timeout and return an empty result marked successful. A failure silently becomes a confident wrong answer, and nothing looks broken enough to recover from.
  • Let one subagent failure terminate the whole workflow. Partial results with an annotated coverage gap beat no report at all.
Takeaway
  • A tool that ran and failed returns isError: true inside a result — that is the only channel Claude can read.
  • Category, a retryable boolean, and a message that says what to do: that is the minimum useful payload.
  • "Timed out" and "no matches" are different answers. Never send them the same way.

Task Statement 2.3

Distribute tools appropriately across agents and configure tool choice

Your support agent works. So the team keeps adding to it — marketing wants promo emails, ops wants inventory checks. Eighteen tools later it starts offering a discount code in the middle of a refund conversation.

Why it's tested

Two separate levers sit inside one task statement, and the exam tests both. Half the questions describe an agent that has drifted outside its role, where the tempting fix is to give it more tools so it stops needing round trips. The other half hinge on one precise distinction: "any" guarantees a tool call, forced selection guarantees that tool.

Start hereTwo terms this section depends on

Scoped tool access
Giving an agent only the tools its role needs, rather than everything the organisation owns. A tool the agent doesn't hold cannot be misused, no matter what the prompt says.
tool_choice
A request parameter that controls whether Claude must call a tool on this turn, and optionally which one. It governs a single turn — not the shape of the whole conversation.

MechanismWhat eighteen candidates does to a decision

Same agent, same customer message. Flip between the toolkit it has today and the one its role actually needs.

Interactive · one shared toolkit vs. role-scoped sets
One agent, 18 candidates. Every turn is an 18-way choice, and the tools furthest from the current task are the ones most likely to be picked by mistake.

KnowledgeScope, and the four tool_choice settings

  • Tool count degrades selection reliability. The exam guide's own figure: 18 tools where 4–5 would do.
  • An agent given tools outside its specialization tends to misuse them. That is the mechanism behind the promo code appearing in a refund conversation.
  • Scoped access means each agent holds its role's tools, plus a deliberately small number of cross-role tools for specific high-frequency needs.
  • With "any" or forced selection, the API prefills the assistant turn. The model emits no natural-language text before the tool_use block.

The four tool_choice settings, and what each one actually guarantees.

"auto"default

Claude decides whether to call a tool at all.

tool_choice: {"type":"auto"}

Guarantees Nothing. It may answer in prose instead.

"any"forces a call

A tool must be called. Which one is still Claude's choice.

tool_choice: {"type":"any"}

Guarantees Some tool call. Never conversational text.

forcednames the tool

One specific named tool must be called on this turn.

tool_choice: {"type":"tool",
  "name":"get_customer"}

Guarantees That exact tool, this turn only.

"none"blocks calls

No tool may be called. The default when no tools are supplied.

tool_choice: {"type":"none"}

Guarantees A text-only answer.

Do not confuse this with Task Statement 1.4. Forcing get_customer with tool_choice makes it the call on one turn. It does not stop the agent calling process_refund three turns later without verification. Ordering that must hold across a whole conversation is a programmatic prerequisite — a hook — not a tool_choice setting. The exam has correct answers of both kinds, and they are not interchangeable.

SkillNarrowing a tool that can do too much

Scoping isn't only about how many tools an agent holds. A single tool can be too broad on its own.

Generic

One tool, any field

update_account(customer_id,
               field, value)

field: "shipping_address"
field: "email"
field: "account_tier"   ← oops
field: "credit_balance" ← oops

Every field the backend exposes is reachable. The only thing standing between a support agent and a customer's credit balance is a prompt instruction.

Constrained

One tool, one job

  customer_id, address)

// validates the address,
// touches nothing else

The dangerous fields are no longer in the agent's reach at all. The boundary is structural rather than instructed — same principle as scoping the toolkit, applied inside one tool.

As the exam words it

The guide teaches this same narrowing move with a research tool: replacing a generic fetch_url — which will retrieve anything on the internet — with load_document, which validates that the URL is actually a document first.

It also gives the scoped cross-role case, in the multi-agent research scenario. A synthesis agent needed simple fact checks for about 85% of its verifications, so it was given a narrow verify_fact tool for those, while genuinely complex verification kept routing back through the coordinator. The wrong answer there is handing the synthesis agent the entire web-search toolkit.

And the forced-selection example is an extraction pipeline: tool_choice: {"type": "tool", "name": "extract_metadata"} on the first request, so metadata extraction runs before any enrichment tool, then "auto" for the turns after it.

SkillApplying both levers

  • Restrict each agent's tool set to its role. A support agent without send_promo_email cannot offer a discount code mid-refund.
  • Add a narrow cross-role tool for the high-frequency case instead of opening up a whole toolkit.
  • Force the first call when a specific tool must run first on that turn, then hand the rest of the conversation back to "auto".
  • Use "any" when you need a structured call rather than prose, but don't care which schema the model picks.
The decision test Does this agent's role explain why it holds this tool? If you have to reach for "well, sometimes it might need it," the tool belongs to another agent — or behind a narrower one.

Anti‑patternOver-provisioning and over-forcing

  • Handing an agent a whole toolkit to eliminate round trips. It dissolves the role boundary that made the system predictable, to solve a problem one scoped tool would have solved.
  • Leaving tool_choice on "auto" when the pipeline needs a guaranteed structured call. The model is free to answer in prose, and downstream parsing breaks intermittently.
  • Forcing one named tool for the whole conversation rather than just the first turn. The agent can never move past that step.
Takeaway
  • Fewer, role-scoped tools select more reliably than one large shared set.
  • "any" guarantees a tool call; {"type":"tool","name":…} guarantees that tool.
  • tool_choice governs one turn. Ordering across a conversation needs a hook.

Task Statement 2.4

Integrate MCP servers into Claude Code and agent workflows

The four tools your agent uses — get_customer, lookup_order, process_refund, escalate_to_human — are served by an MCP server your team wrote. A new engineer clones the repo and none of them are there. Yours work fine. The difference is one file.

Why it's tested

Two facts here look like configuration trivia and are not. The first is the scope table — a teammate who doesn't have your server almost always has it in the wrong file. Start hereThree terms this section depends on

Server scope
Which file an MCP server is configured in. Scope decides who gets the server — just you, just this project, or everyone who clones the repo.
Variable expansion
Placeholder syntax in a config file that is replaced from the environment at load time. It lets a committed file reference a secret without containing one.
MCP resource
Content a server exposes at a URI, listed with resources/list and fetched with resources/read. A resource is something to read — unlike a tool, which is something to do.

MechanismWhat happens when the session starts

Each configured scope connects. Every server's tools land in the same pool, and the agent sees all of them at once.

Interactive · the same repo, opened on two machines
Choose whose machine this is — the servers that connect change with it.

Expansion has a fallback form and a defined reach. ${VAR} takes the environment value; ${VAR:-default} falls back when it isn't set. Expansion works in command, args, env, url and headers. The exam guide writes the same idea as ${GITHUB_TOKEN} against a GitHub server — expect either spelling in an item. More precise than the guide. The guide names two scopes, and those two are the exam answer. Claude Code has three. Alongside project (.mcp.json) and user (~/.claude.json, all your projects) there is local — the default when you run claude mcp add with no --scope. Local also lives in ~/.claude.json, but keyed to one project's path. When the same server name appears at more than one scope, precedence runs local, then project, then user. Learn the guide's two-way split for the exam; know the third so your own configs behave.

KnowledgeDiscovery, and the other primitive

  • Tools from every configured server are discovered when the connection is established. All of them are available to the agent simultaneously.
  • A tool is an action the model invokes. A resource is content the server exposes at a URI for reading.
  • Resources are how you tell an agent what exists without it spending tool calls to find out. For the support agent, that means the refund policy documents, the product catalog, and the current known-issues list. The guide's own examples are issue summaries, documentation hierarchies and database schemas.
  • An agent that can see the policy catalog up front stops guessing at policy and stops probing for it one call at a time.

Anti‑patternConfig mistakes with real consequences

Takeaway

Select and apply built‑in tools (Read, Write, Edit, Bash, Grep, Glob) effectively

Scenario switch This is the one section in Domain 2 that leaves the support agent. Everything else in this domain stays with the support agent.

Six tools that look too basic to be worth testing. The exam tests the edges instead: what Edit does when its anchor isn't unique, and how to explore a codebase without reading all of it.

Why it's tested

Nobody gets a question asking what Read does. The questions describe a symptom — an edit that keeps failing, a context window that filled up during exploration, a function whose callers you can't find — and ask which tool choice fixes it. Underneath almost every one is the same distinction: Grep searches contents, Glob matches paths.

MechanismThe distinction the whole task statement rests on

You need to find every place calculateShippingTotal is called. One of these tools can do it and the other cannot.

Searches contents

Grep

Grep("calculateShippingTotal")

src/checkout/cart.ts:42
src/checkout/summary.ts:118
src/api/orders.ts:7
tests/cart.test.ts:91

Looks inside files. Built on ripgrep, so patterns use ripgrep regex rather than POSIX grep syntax, and it respects .gitignore.

Use for: callers of a function, an error message string, an import statement.

Matches paths

Glob

Glob("**/calculateShipping*")

// no matches —
// no file is NAMED that

Only ever looks at filenames. Never opens a file. Does not respect .gitignore by default.

Use for: **/*.test.tsx — every test file at any depth, wherever it lives.

The decision test Am I looking for something inside a file, or for the file itself? Inside → Grep. The file itself → Glob. Contents versus paths answers most questions in this task statement.

KnowledgeThe other four

Read

Returns a file's contents with line numbers. A file over the token limit comes back as a first page with a PARTIAL view notice.

Use it whenYou need the whole file, or the file an import pointed you to.

Write

Creates a file, or overwrites one completely. There is no partial write.

Use it whenThe file is new, or you are replacing all of it — including the Read + Write fallback.

Edit

Exact string replacement: old_string becomes new_string. No regex, no fuzzy matching, and one character of whitespace is enough to miss.

Use it whenYou are changing one place in a file you have already read.

Bash

Runs a shell command. A cd carries over while it stays inside the project; an export does not carry over at all.

Use it whenNo dedicated tool does the job — running tests, a build, git.

Read before you edit. Edit expects the file to have been read earlier in the same conversation, and a read that stopped at a PARTIAL view notice does not count. The docs note that newer models can skip the read when it would not need a permission prompt — but the habit, and the exam's assumption, is read first.

SkillWhen Edit refuses

You ask the agent to change one timeout in config.ts. The edit is rejected, and re-running it produces the identical rejection.

Interactive · an Edit that can't find a unique anchor
One Edit, three outcomes. old_string is timeout: 3000,.
Three identical matches means no unique anchor. Edit rejects rather than guessing, and it will reject identically every time. Time reads downward.
More precise than the guide. Edit requires old_string to appear exactly once, because applying it to a guess would be worse than refusing. The guide's fallback is Read the full file, then Write it back — that is the exam answer. The docs describe two other resolutions: widen old_string with surrounding lines until one occurrence matches, or set replace_all: true, which changes every occurrence and is only right when that is what you meant.

SkillExploring 900 files without reading 900 files

The engineer asks how a refund flows through the system. Two ways to answer it.

Exhaustive

Read everything first

Glob("**/*.ts")   → 900 files
Read(...) × 900

The context window fills with files the question never needed, and the few relevant details end up buried in the middle where they are least reliably recalled.

Incremental

Follow the thread

  → src/api/refunds.ts:31
Read("src/api/refunds.ts")
  → imports refundPolicy
Grep("refundPolicy")
Read("src/domain/policy.ts")

Four calls instead of nine hundred, and every file in context is one the question actually touches.

The wrapper-module trap. To trace a function used through a re-export, searching the original name isn't enough — every call that goes through the wrapper uses a different name. First identify all the exported names the wrapper exposes, then Grep for each of those exported names across the codebase.

SkillTool selection in practice

  • "Find all callers of calculateTotal" is Grep. "Find every **/*.test.tsx" is Glob.
  • When Edit can't find a unique anchor, widen old_string with neighbouring lines first — it is cheaper than rewriting the file.
  • Fall back to Read plus Write when no surrounding context makes the anchor unique.
  • Start from an entry point and follow imports, rather than loading the repository up front.

Anti‑patternThree habits that cost context or fail silently

  • Reading every file in the repository before answering anything. It fills the context window with material the question never needed.
  • Using Glob to find where a function is called. Glob matches filenames; it never looks inside a file.
  • Re-running the same failing Edit and expecting a different result. A non-unique old_string fails deterministically — change the anchor or change the tool.
Takeaway
  • Grep searches contents; Glob matches paths. That one line answers most of these questions.
  • Edit fails on a non-unique old_string — widen the anchor, or fall back to Read + Write.
  • Explore incrementally from an entry point rather than reading the whole repository first.

Task Statement 3.1

Configure CLAUDE.md files with appropriate hierarchy, scoping, and modular organization

You wrote the team's commit conventions into a CLAUDE.md months ago. Claude has followed them in your sessions ever since. A new engineer joins, clones the repo, and Claude ignores every one of them.

Why it's tested

The symptom in these items is always the same: an instruction works for one person and not another. The wrong answers blame the instruction. They say it needs rewording, emphasis or repetition. The right answer is almost always about which file it is sitting in. Scope is the mechanism. Wording is the distraction.

KnowledgeWhat actually loads, and in what order

A session started in packages/api/ of your monorepo. This is what happens before you have typed anything:

  1. You start Claude Code in packages/api/.
  2. It reads the managed policy file, if one exists, and your ~/.claude/CLAUDE.md.
  3. It reads the CLAUDE.md, and any CLAUDE.local.md, in the launch directory and in every directory above it.
  4. It concatenates everything it found into context, from the top of the tree down. The launch directory's file is read last.
  5. Later, when Claude reads a file in a subdirectory such as src/, that directory's CLAUDE.md is added.
Interactive · step through the load order
Step through what loads before your first message.
Amber rows are committed to the repository. They are the only rows a teammate's clone carries.

More precise than the guide. The exam guide names three levels: user, project and directory. Claude Code has two more. Managed policy sits above them, and CLAUDE.local.md sits beside each project file. Answer the exam with the guide's three. Expect the extra two in your own repositories.

  • At launch, Claude Code reads the CLAUDE.md in the launch directory and in every directory above it. For packages/api/ that is three project files, not one.
  • Only committed files are shared. A teammate's clone carries the amber rows and nothing from your ~/.claude/.
  • A CLAUDE.md in a subdirectory below the launch directory is not loaded at launch. It loads when Claude reads a file in that directory.
  • That on-demand file is the guide's directory-level tier. It is bound to one directory, so it cannot cover a file type spread across the repository. Task Statement 3.3 handles that case.

"Hierarchy" does not mean "override". Every discovered file is concatenated into context, from the filesystem root down to your working directory. Nothing at a narrower scope deletes an instruction from a broader one. Two files that contradict each other leave Claude to pick one arbitrarily. That is why the docs tell you to prune contradictions rather than rely on precedence.

KnowledgeWho closes the loop

  2. You ask Claude to implement, then run the suite.
  3. The failures come back into the conversation, each named, with expected versus actual.
  4. Claude reads them and changes the code.
  5. The cycle repeats until the suite passes. You review a green suite, not every attempt.

Task Statement 4.1

Design prompts with explicit criteria to improve precision and reduce false positives

Scenario switch This section runs on the exam guide's Claude Code for Continuous Integration scenario. The pipeline reviews every pull request and posts findings as inline comments. The guide writes this task statement in review vocabulary, so the review bot is the system here. The principle carries straight back to extraction: an extracted value the document does not support is a false positive too.

The review bot posts about forty comments on every pull request. Most are about comment wording and variable names. Developers have started resolving them unread, including the one last week that pointed at a real SQL injection.

Why it's tested

The wrong answers all ask the model to be more careful. "Be conservative." "Only report high-confidence findings." Add a confidence threshold. None of them says which findings are unwanted, so the model drops findings without regard to category. Real issues go with the noise. The item is checking whether you know that precision comes from naming categories, not from asking for caution.

Start hereThree terms this section leans on

precision
Of the findings reported, the share that are real. Forty comments with ten real issues is 25% precision.
categorical criterion
An instruction that names a class of finding and says whether to report it. "Report SQL built from user input" is one. "Be thorough" is not.
severity level
A label on each finding saying how much it matters. It is only consistent when each level is defined by examples, not by adjectives.

The mechanism, one review at a time

  1. The pipeline sends the diff and the review prompt.
  2. Claude finds candidate issues. Some are real bugs. Some are style, local patterns, or wording.
  3. For each candidate, the prompt is the only thing deciding whether it gets reported.
  4. A vague instruction leaves that decision to the model's reading of words like "accurate" or "important". Each run resolves it differently.
  5. A categorical instruction answers the decision for the whole class. Style is skipped every time. Injection is reported every time.

Explicit

  • Explicit criteria beat vague instructions because they move the report-or-skip decision from the model's judgement into the prompt.
  • "Be conservative" and "only report high-confidence findings" do not improve precision compared with categorical criteria. They change how many findings appear, not which kind.
  • False positives have a cost beyond the wasted comment. A category with a high false positive rate teaches developers to ignore the bot, and they then ignore the accurate categories too.
Ask one question: could two careful reviewers read this instruction, look at the same diff, and disagree about what to report? Yes → it is a vague instruction. Replace it with named categories to report and to skip. No → it is a criterion, and adding "be careful" to it will not make it more precise.

SkillSeverity defined by code, not adjectives

"Critical", "major" and "minor" mean different things on different runs. A concrete code example for each level fixes the boundary where it is usually argued.

SkillRestoring trust while you fix a noisy category

  • Write criteria that say which issues to report, such as bugs and security, and which to skip, such as minor style and local patterns. Do not rely on confidence-based filtering to do it.
  • Temporarily disable the category with the highest false positive rate. Developers start reading the comments again because the remaining categories are accurate.
  • Rewrite that category's criterion offline, measure it against past pull requests, and turn it back on only when its precision matches the rest.
  • Define each severity level with a concrete code example, so two runs classify the same finding the same way.

Redefine what Important means for your repository. List categories and paths to skip, and cap the number of nits. Set a verification bar, such as requiring a file:line citation for any behaviour claim. It is not named in the exam guide. It is a useful model for writing criteria.

Anti-patternFixes that change volume, not precision

  • "Only report findings you are highly confident in." The model's confidence is not sorted by category, so real issues are dropped alongside noise.
  • A numeric confidence threshold on self-reported scores. The same problem with a number attached. Domain 5 covers why self-reported confidence needs calibrating before it routes anything.
  • Leaving a noisy category on while you tune it. Every false positive it posts in the meantime costs trust in the categories that were already right.
Takeaway
  • Precision comes from naming what to report and what to skip. "Be conservative" changes volume, not accuracy.
  • One high-false-positive category erodes trust in every category, so switch it off while you fix it.
  • Severity is consistent only when each level is defined with a concrete code example.

Task Statement 4.3

Enforce structured output using tool use and JSON schemas

The nightly ledger import used to crash on malformed JSON about once a week. The team moved extraction onto a tool with a JSON schema and the crashes stopped. A month later, finance found invoices in the ledger with due dates that appear nowhere in the documents.

Why it's tested

Two claims get merged in the wrong answers. Tool use with a schema does eliminate JSON syntax errors. It does not make the values right. Items also plant the opposite trap: a schema that marks every field required looks rigorous, but it forces the model to produce a value for a field the document does not contain. input_schema
The JSON schema on a tool definition. For an extraction tool, it is the shape of the record you want back.

Task Statement 4.4

Implement validation, retry, and feedback loops for extraction quality

The validator rejects about six in every hundred invoices. The pipeline retries each rejected invoice three times. Half of them pass on the first retry. The other half fail all three retries, every night, because the purchase order number they need lives in a master contract nobody sent.

Why it's tested

Items test two judgements. The first is what a retry must carry: the original document, the failed extraction, and the specific validation errors. "Try again" carries none of them. The second is when not to retry at all. A retry can correct how the model read the document. It cannot supply a value the document does not contain. The wrong answers add retries, raise the retry count, or switch model when the value was never in the input.

Start hereThree terms this section adds

A follow-up request that includes the specific validation errors, so the model knows what to correct instead of guessing.

Two fields for one quantity. One is the total as printed. The other is the sum of the extracted line items. A difference between them is a signal your code can check.
conflict_detected
A boolean the model sets when the source document contradicts itself. It separates "the extraction is wrong" from "the document is inconsistent".

The mechanism, one rejected record at a time

  1. The extraction returns a schema-valid record. Its shape is guaranteed. Its values are not.
  2. Your validator checks what the schema cannot express: sums, formats, and rules across fields.
  3. If the record fails, your code decides whether the correct value is present in what it sent.
  4. If it is present, the retry sends the original document, the failed extraction, and the specific errors. The model corrects against a concrete target.
  5. If it is absent, no retry can produce it. The record keeps null or a conflict flag and goes to human review.

The extraction system has two workloads. Suppliers upload an invoice and wait on the page while it is checked. Separately, about ten thousand scanned documents a day must be in the ledger within 30 hours of arriving. Your manager proposes moving both to the Message Batches API to halve the cost.

Why it's tested

So the discriminator is whether anyone is waiting on the result. Items also test the arithmetic of fitting that 24-hour window inside a longer SLA, and what to resubmit when some requests in a batch fail.

Start hereThree terms this section adds

custom_id
Your identifier on each request in a batch. Results come back in any order, so it is the only reliable way to match a result to its document.
processing window
The time a batch may take. Most finish in under an hour, but the only bound is 24 hours. Requests still unfinished then expire.
blocking workflow
A workflow where a person or a pipeline cannot continue until the result arrives. A supplier on an upload page. A pre-merge check.

The mechanism, one batch at a time

  1. You create a batch: a list of requests, each with a custom_id and the same params a normal Messages call takes.
  2. The batch's processing_status is in_progress. Nothing comes back yet.
  3. You poll. When every request has finished, or 24 hours have passed, the status becomes ended.
  4. You fetch the results. They are in any order, so you join them back to documents by custom_id.
  5. Each result is succeeded, errored, canceled or expired. You resubmit only the ones that did not succeed.

KnowledgeWhat the batch API gives you, and what it does not

  • All usage is charged at 50% of standard API prices.
  • Results are available when every request has finished or after 24 hours, whichever comes first. There is no guaranteed latency within that window.
  • Results can come back in any order. The docs' instruction is to always match them by custom_id.
  • A request in a batch cannot run a tool on your side mid-request and then continue. If Claude asks for your tool, that request ends there, and answering it takes a new request.

More precise than the guide. The guide says the batch API "does not support multi-turn tool calling within a single request." That is the exam answer, and it is the mechanism for tools you run. A batch request can contain a prior conversation, including earlier tool calls and results, and Anthropic-run server tools such as web search do execute inside it. What no single request can do is pause for your code to run a tool and resume. So a multi-step agentic loop over your own tools belongs on the synchronous API, and a single-turn extraction belongs in a batch.

Task Statement 4.6

Design multi-instance and multi-pass review architectures

Scenario switch This section runs on the exam guide's Claude Code for Continuous Integration scenario. The pipeline now generates code as well as reviewing it. Who reviews that code, and with what in their context, is the whole question. The same design applies to the extraction system when a second pass checks the first pass's records.

A CI job has Claude implement a token-refresh fix across three files. The same session is then asked to review its changes. It reports no issues. The fix ships with a race between refresh and logout that the generating session had considered and judged acceptable.

Why it's tested

Every wrong answer keeps the reviewer inside the generator's context. It adds a self-review instruction, turns on extended thinking, or asks the same session to "check carefully". The flaw is not effort. The session that wrote the code still holds the reasoning that justified it, so it re-reaches the same conclusions. Items test whether you move the review to an instance that never saw that reasoning.

Start hereThree terms this section adds

reasoning context
The decisions, assumptions and rejected options a session accumulated while producing its output. They stay in its context window as settled facts.
independent review instance
A separate Claude invocation, with its own context window, given only the artifact to review and the review criteria.
integration pass
A review pass that looks only at how files interact, such as data flow across modules, after each file has had its own local pass.

The mechanism, one review architecture

  1. The generating session produces the diff. Its reasoning stays in its own context window.
  2. Only the diff and the review criteria are passed to new instances. The reasoning is deliberately left behind.
  3. Each changed file gets a local pass in its own instance, so every file gets the same depth of attention.
  4. A separate integration pass looks at the cross-file data flow the local passes cannot see.
  5. Every finding carries a self-reported confidence. Routing uses it: confident findings are posted, uncertain ones go to a verification pass or a person.

More precise than the guide. That is not a contradiction. A self-check against explicit test criteria catches mistakes the model can see. It does not catch a decision the model already judged correct. The docs' own review chain also runs "generate a draft → review it against criteria → refine" as separate API calls, which is where the independence comes from. For the exam, the answer to "catch subtle issues in generated code" is a second, independent instance.

Ask one question: does the reviewer's context contain the reasoning that produced the code? Yes → it is self-review, however it is worded, and adding thinking does not change that. Start an independent instance with only the diff and the criteria. No → it is an independent review, and splitting it per file plus one integration pass is how it stays thorough on large changes.

SkillSplitting a large review into passes

  • Give each changed file its own local pass. One pass over fourteen files spreads attention thin, which produces uneven depth and contradictory findings across files. Task Statement 1.6 covers that failure in detail.
  • Run a separate integration pass for cross-file data flow. It is the only pass that sees how refresh.ts and logout.ts interact.
  • Run every pass in an instance without the generator's reasoning. Multi-pass and multi-instance are two separate fixes, and a large generated change needs both.

What this looks like in the product. Claude Code's managed Code Review is built this way. A verification step then checks each candidate against actual code behaviour to filter out false positives, before findings are deduplicated and ranked by severity.

Task Statement 5.1

Manage conversation context to preserve critical information across long interactions

A customer opens a billing dispute and a late-delivery complaint in the same chat. The conversation runs to thirty turns. At turn 26 the agent is still in the same conversation, but it is no longer working from the same facts.

Why it's tested

The wrong answers treat a long conversation as a size problem. Use a bigger context window. Summarise more often. Tell the model to remember the amount. The item is checking three things. Summaries lose exact values. Tool results fill the window with fields nobody needs. Position in a long input changes what gets used. The fix is structural: take the facts out of the history and give them a block of their own.

Start hereThree terms this section leans on

transactional fact
A value the next action depends on exactly: an amount, a date, an order number, a status. "About $200" is not a transactional fact. "$212.40" is.
trimming
Your code keeping only the fields of a tool result that the task needs, before the result is appended to the history.
context layer
A section of the prompt your code assembles separately from the conversation, such as a case facts block. It is rebuilt each turn rather than accumulated.

The mechanism, one long conversation

  1. Every request carries the whole conversation. The Messages API is stateless, so the history is the agent's only memory of the case.
  2. Each lookup_order result appends about forty fields. The agent needed five of them, and all forty are re-sent on every later turn.
  3. The history approaches its budget, so older turns are replaced by a summary.
  4. The summary keeps the gist and drops the specifics. "$212.40, agreed in turn 4, to the original card by 11 March" becomes "a partial refund of around $200 was discussed".
  5. At turn 26 the agent acts on the summary. process_refund is called with 200.00.
  6. The fix: your code extracts each transactional fact into a case facts block at the top of every prompt, and trims tool results before they are appended. The summary can then lose what it likes.

Task Statement 5.2

Design effective escalation and ambiguity resolution patterns

The agent resolves 55% of contacts on first contact, against an 80% target. The logs show a pattern. It escalates standard damage replacements that arrive with photo evidence, and it tries to handle policy exceptions by itself.

Why it's tested

The wrong answers replace a decision rule with a proxy. Escalate when sentiment turns negative. Escalate when the model's self-reported confidence is low. Train a classifier. Sentiment measures how the customer feels, and a self-reported score measures how the model feels about itself. Neither measures whether the case needs a human. The item is checking whether you know the actual triggers, and whether you would write them down as criteria with examples.

Start hereThree terms this section leans on

escalation trigger
A condition that means a human should take the case. The guide names three: the customer asks for one, policy has a gap or needs an exception, or the agent cannot make meaningful progress.
policy gap
A request the written policy is silent or ambiguous about. The agent has no rule to apply, so any answer it gives is an invented policy.
disambiguation
Asking the customer for an additional identifier when a lookup returns more than one match, instead of choosing one of the matches.

The mechanism, one incoming turn

  1. Has the customer asked for a human? If so, the agent escalates now, without investigating first.
  2. Did get_customer return more than one match? If so, the agent asks for another identifier before touching either account.
  3. Does written policy cover this exact request? If it is silent or ambiguous, the agent escalates. A complex case that policy does cover is not a reason to escalate.
  4. Can the agent make meaningful progress? If not, it escalates with what it tried.
  5. Otherwise it resolves the case. If the customer is frustrated, it acknowledges that and offers the fix. It escalates only if the customer then repeats that they want a person.

Task Statement 5.3

Implement error propagation strategies across multi-agent systems

Scenario switch This section runs on the exam guide's Multi-Agent Research System. A coordinator delegates to web search, document analysis, synthesis and report subagents. The guide writes this task statement about coordinators and subagents, so the research system is the system here. The support agent meets the same problem at one level down, in Task Statement 2.2.

The research system is writing a report on grid-scale battery storage costs. The coordinator sends four searches to the web search subagent. Three succeed. The one on national incentive programmes times out, and what happens next depends entirely on what the subagent sends back.

Why it's tested

Every wrong answer here looks like tidy engineering. Catch the timeout and return an empty list. Retry, then report "search unavailable". Raise the exception and stop the run. Each one hides the failure from the only agent that could route around it, or throws away the work that succeeded. The item is checking whether you design the subagent's failure report for the coordinator's next decision.

Start hereThree terms this section leans on

structured error context
A failure report with four parts: the failure type, what was attempted, any partial results, and possible alternatives.
access failure
The source could not be reached: a timeout, an outage, a refused connection. Nothing is known about what the source contains.
coverage annotation
A note in the synthesis output saying which findings are well supported and which topic areas have gaps because sources were unavailable.

The mechanism, one failed search

  1. The coordinator delegates four searches. Each subagent runs in its own context window, so the coordinator learns only what is returned.
  2. The incentives search times out. A timeout is transient, so the subagent retries locally, twice, with backoff.
  3. It still fails. The subagent now propagates the error, because it cannot resolve it.
  4. It returns the failure type, the query it attempted, the two sources it did retrieve, and an alternative: a government registry.
  5. The coordinator chooses. It can retry a narrower query, try the alternative source, or proceed with partial results.
  6. The synthesis output says which areas are thin, so the reader can see the gap instead of trusting a silence.

  • Terminating the whole workflow on one failure is the opposite mistake. It discards every search that worked.

  • Propagate only the errors it cannot resolve, with what was attempted and any partial results attached.

Task Statement 5.4

Manage context effectively in large codebase exploration

The team behind the support agent is moving process_refund to a new payments provider. An engineer uses Claude Code to trace every dependency of the refund flow through the agent's 1,400-file backend. Two hours in, the answers start to sound like a textbook instead of like this codebase.

Why it's tested

The tempting answers keep all the work in one conversation and hope it fits: a bigger context window, one more push, or starting over from nothing. The item is checking whether you recognise context degradation from its symptom, and whether you know the four tools against it. Findings go into a scratchpad file. Verbose work goes to subagents. Each phase starts from a summary of the last one. Agent state goes to disk so a crash costs minutes, not the session.

Start hereThree terms this section leans on

context degradation
Answers in an extended session becoming inconsistent, and citing "typical patterns" instead of the specific classes found earlier. Anthropic's docs call the underlying effect context rot.
scratchpad file
A file the agent writes its key findings to as it works, and reads back when a later question needs them. It lives on disk, outside the context window.
manifest
A file at a known location listing each agent, its status, and where its exported state is. The coordinator loads it on resume.

The mechanism, three phases of exploration

  1. Phase 1 finds all test files. A subagent does the searching in its own context window and returns a short summary.
  2. The main agent writes the key paths from that summary to a scratchpad file.
  3. Phase 2 traces refund flow dependencies. Phase 1's summary is injected into the new subagent's first prompt, so it does not rediscover it.
  4. Every agent exports its state to a known directory as it goes, and a manifest records where each export is.
  5. Phase 3 asks a specific question. The main agent reads the scratchpad before answering, instead of relying on history that may have been summarised.
  6. If the session crashes, the coordinator loads the manifest on resume and injects each agent's state into its prompt.

  • Carrying on after answers start citing "typical patterns". That is the symptom of degradation. Write the findings down and start the next phase from a summary.
  • Restarting a crashed exploration from nothing. Without state exports and a manifest, finished phases are repeated in full.

Task Statement 5.5

Design human review workflows and confidence calibration

A QA team reviews a sample of the tickets the agent resolves by itself. The dashboard says those resolutions are 97% accurate, and the proposal on the table is to stop reviewing them. The agent's case facts extraction also reports a confidence score for each field.

Why it's tested

Two numbers look trustworthy and are not, yet. An aggregate accuracy figure can hide one segment that fails badly, because the large segments outvote it. A confidence score straight from the model is not a probability until it has been checked against labelled outcomes. The item is checking whether you segment before you automate, calibrate before you route, and keep sampling after you cut review.

Start hereThree terms this section leans on

segment
A slice of the traffic measured on its own: a ticket type, a document type, or a single field. Accuracy is only known for a segment you have measured.
stratified random sampling
Sampling randomly within each segment, with a set number per segment, so small segments get enough reviews to measure. A plain random sample mostly reviews the largest segment.
labelled validation set
Past cases where a human has recorded the correct answer. Comparing the model's scores against it is what calibrates them.

The mechanism, before review is reduced

  1. Measure accuracy by segment: ticket type first, then each field within the weakest type.
  2. Have the model output a confidence score for each field it extracts.
  3. Compare those scores with a labelled validation set, and set the review threshold where observed accuracy is acceptable.
  4. Route below-threshold fields, and cases with ambiguous or contradictory source information, to human reviewers first.
  5. Reduce review only in segments that have passed. Keep stratified random sampling of high-confidence cases everywhere, to measure the error rate and catch new error patterns.

Stratified random sample

200 reviews, a fixed share per segment

  • Analyse accuracy by ticket type and by field, and confirm consistent performance across every segment before reducing human review.
  • Have the model output field-level confidence scores, then set review thresholds from a labelled validation set.
  • Route low-confidence fields, and cases whose source information is ambiguous or contradictory, to human review first. Reviewer capacity is limited, so it goes where errors are likeliest.
As the exam words it

The guide writes this task statement about extraction: aggregate accuracy (for example, 97% overall) that masks poor performance on specific document types or fields, and validating accuracy "by document type and field segment before automating high-confidence extractions".

  • Cutting review because overall accuracy is high. The largest segments dominate the mean, and the smallest failing one disappears into it.

  • Stopping all review once a segment passes. Without continued sampling, a new error pattern has no way to be noticed.
Takeaway

  • Field-level confidence routes review only after thresholds are calibrated on a labelled validation set.
  • Keep stratified random sampling of high-confidence cases to track error rates and catch new patterns.

Task Statement 5.6

Preserve information provenance and handle uncertainty in multi-source synthesis

Scenario switch This section runs on the exam guide's Multi-Agent Research System, as 5.3 did. The battery storage report is still being written. This time nothing failed: three sources were found, they disagree, and the question is what reaches the report.

Three credible sources give three prices for battery packs: $139, $115 and $124 per kWh. The draft report says "$124/kWh" with no source. One of the other two figures is simply older. The other is a genuine disagreement. The draft cannot tell them apart any more.

Why it's tested

The instinct is that synthesis should produce one clean answer. So the wrong answers pick the most recent value, average the values, or trust the most authoritative-sounding source. Each one discards information the reader needed. The item is checking three habits. Keep claim-source mappings intact through every step. Annotate conflicts instead of resolving them silently. Require dates, so an old figure is not read as a contradiction.

Start hereThree terms this section leans on

provenance
Where a claim came from: the source, the passage, and the date. It is lost the moment a finding is compressed without its source attached.
contested finding
A claim on which credible sources disagree for the same period and scope. It is reported with each value and its source, not settled by the model.
temporal difference
Two values that differ because they describe different times. Without dates, it looks exactly like a contradiction.

The mechanism, three sources to one report

  1. Each subagent returns findings as structured claim-source mappings: the claim, the source URL or document name, the relevant excerpt, and the publication or collection date.
  2. Document analysis completes with every value included. Where values conflict, it annotates the conflict instead of choosing.
  3. The coordinator decides how to reconcile the conflict before passing the findings on to synthesis.
  4. The synthesis subagent merges the mappings. It may shorten the prose, but it keeps every claim attached to its source.
  5. The report separates well-established findings from contested ones, keeps each source's own characterisation and method, and renders each content type in its natural form.
