# Superpowers on Kiro — compatibility findings

What had to change to make [obra/superpowers](https://github.com/obra/superpowers)
behave on Kiro the way it behaves on Claude Code, and what still differs.

**Upstream:** v6.2.0, commit `44c9b2d` (MIT)
**Port shape:** C (instructions-file) — see upstream `docs/porting-to-a-new-harness.md`
**Design record:** [`specs/2026-06-10-superpowers-port.md`](specs/2026-06-10-superpowers-port.md)

## The two rules a port must not break

1. **Skills name actions, not tools — never edit skill bodies.** Upstream skill
   text is already harness-neutral (no `Task`, no `TodoWrite`, no
   `${CLAUDE_PLUGIN_ROOT}`); it runs on Kiro unmodified. A port adds a tool
   mapping and a bootstrap, nothing else.
2. **The bootstrap is the entire integration.** `using-superpowers` must reach
   the model at the start of every session with no per-session opt-in. Without
   it the skills are present on disk and never invoked.

## Breaking issues found, and the fix

| # | Issue | Impact | Fix |
|---|---|---|---|
| 1 | Skill bodies were condensed (TDD 320→107 lines, subagent-driven-development 503→67, systematic-debugging 283→59) | The rules upstream tunes for — the Iron Law, the red-flag tables, the fix-loop bounds — were gone, so the agent rationalized past them | Vendored verbatim |
| 2 | Workflows lived as `references/*.md` under one router skill, with no frontmatter | Kiro matches on `name`/`description` to auto-activate. Files without frontmatter can never trigger, and none registered as slash commands | 14 standalone skills at `skills/<name>/SKILL.md` |

## Why the bootstrap is steering, not a hook

Kiro's five hook events are `agentSpawn`, `userPromptSubmit`, `preToolUse`,
`postToolUse`, `stop`. Only `userPromptSubmit` has its stdout added to the
conversation — and that fires per *turn*, not per session. `agentSpawn` fires at
the right moment but its stdout is not injected. So Kiro has no shell-hook
session-start surface (upstream Shape A is unavailable).

What Kiro does have: **`kiro-cli` ignores `inclusion:` frontmatter and loads
every file in `.kiro/steering/` automatically.** That is a guaranteed,
no-opt-in, session-start injection — upstream Shape C, the shape Gemini uses.

```
skills/using-superpowers/SKILL.md                  ─┐
skills/using-superpowers/references/kiro-tools.md  ─┴─► scripts/gen-superpowers-bootstrap.sh
                                                          └─► steering/superpowers-bootstrap.md
```

Content is **inlined, not `#[[file:...]]`-included**. Upstream's guide documents
harnesses where include syntax degrades into "a hint the model may choose to
read" (it emits a file-read tool call) rather than guaranteed inlining. That is
precisely the guarantee a bootstrap cannot trade away, so it is not used here.

## Mapping corrections

The first mapping was written from Claude Code's tool surface and got five
things wrong about kiro-cli:

| Claim in the old mapping | Reality | Why it mattered |
|---|---|---|
| No native todo tool → "track tasks as `- [ ]` checkboxes in the plan file" | **`todo` is a built-in tool** | `using-superpowers` says "create a todo per checklist item". The agent was being told to hand-roll what a tool does |
| `Glob` → `read`; `Grep` → `read` or `shell` | **`glob`, `grep` and `code` are distinct built-ins** | Search actions map 1:1; no shell fallback needed |
| `WebFetch`/`WebSearch` → `web` | **`web_fetch` and `web_search`** — there is no `web` tool | The named tool did not exist |
| "`/<x>` only works for `inclusion: manual` steering — these references are not" | **Every skill in `.kiro/skills/` registers as `/skill-name`** (CLI ≥ 2.1) | The user-facing invocation path was documented as unavailable |
| `Task` → point subagents at a named agent in `.kiro/agents/` | Kiro ships a built-in **general purpose** subagent ("handles parallelized tasks of any kind using the default agent configuration") with the **same built-in tools as the main agent** | Where a skill says "dispatch a `general-purpose` subagent", that built-in is the direct match. Naming a catalog agent narrows tools and silently changes behavior |

## Kiro-specific behavior the mapping documents

- **No `Skill` tool.** Three sanctioned invocation paths: automatic description
  match, `/skill-name`, or `read` the `SKILL.md`. Upstream's "never read skill
  files manually" means "don't bypass your platform's mechanism" — on Kiro,
  reading `SKILL.md` *is* one of the mechanisms.
- **Subagents inherit steering**, so the bootstrap reaches them. Upstream's
  `<SUBAGENT-STOP>` block is what keeps a dispatched subagent from re-entering
  the skill-selection loop instead of doing its task. It is preserved verbatim.
- **Hooks do not fire on subagents.** Any safety rule must live in the
  subagent's own `toolsSettings` (`write.allowedPaths`, `shell.deniedCommands`),
  never in a parent `preToolUse` hook.
- **Custom agents must opt in.** `kiro_default` sees the skills automatically; a
  custom agent sees only what its `resources` lists:
  `skill://.kiro/skills/*/SKILL.md`.
- **No plan mode.** "Brainstorm before entering plan mode" applies to the
  `kiro_planner` agent and the spec workflow. Superpowers' own plan and spec
  files (`docs/superpowers/plans/…`, `docs/superpowers/specs/…`) are not Kiro
  specs and keep the format `writing-plans` defines.

## Known gaps

- **The acceptance test has not been run.** Upstream's definition of done is a
  clean session where `Let's make a react todo list` triggers `brainstorming`
  before any code is written. That needs an authenticated `kiro-cli`. Run it
  before treating the port as verified.
- **Kiro issue #6680** — `skill://` sometimes loads full skill bodies at startup
  instead of frontmatter only. Across 14 skills that is real context cost. It is
  a Kiro bug, not a port decision.
- **Headless mode** — steering loads the same way under
  `kiro-cli chat --no-interactive`, so the bootstrap applies, but the
  subagent-heavy skills assume an interactive partner.
- **Not submitted upstream.** A PR adding a Kiro shape to obra/superpowers is
  out of scope for this repo; it would require the transcript above.

## Maintenance

```bash
scripts/gen-superpowers-bootstrap.sh --check   # fails if the bootstrap is stale
scripts/gen-superpowers-bootstrap.sh           # regenerate after editing either source
```

Re-vendoring a newer upstream: copy the skill directories verbatim, drop
`systematic-debugging`'s eval fixtures (`test-pressure-1.md`,
`test-pressure-2.md`, `test-pressure-3.md`, `test-academic.md`,
`CREATION-LOG.md`), re-apply the single sanctioned edit
(`- Kiro: references/kiro-tools.md` in `using-superpowers`'s Platform Adaptation
list), then regenerate the bootstrap. Nothing else in a skill body should differ
from upstream — `diff -r` against the upstream checkout should show only those
items plus `references/kiro-tools.md` and `LICENSE`.

Re-check `kiro-tools.md` against kiro.dev on each bump: it asserts live platform
facts (tool names, the built-in general-purpose subagent, unconditional steering
load, slash-command registration), and it ships inside the always-on bootstrap,
so anything stale there is asserted to the model every session.
